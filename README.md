# ant-output-rule

让 Agent 用中文汇报时，说的话能被核对。

一套输出规范，加一个能跑的检查脚本。规范管人怎么写，脚本管机器能查的部分。

## 解决什么问题

Agent 的汇报有三个毛病。

一是读的人核对不了。「应该没问题」这类话，既没法确认，也没法反驳。

二是读不完。结论埋在第三段，证据堆在最前，读者要先看完过程才知道结果。

三是一眼看出是套话。「需要注意的是」「形成闭环」这类词，读者会自动降低信任。

这个规范把汇报拆成固定的层次和固定的词，让读者第一眼知道要不要动手。

## 怎么用

装到 pi 的 skill 目录：

```bash
ln -s ~/workspace/ant-output-rule ~/.pi/agent/skills/ant-output-rule
```

然后 `/reload`，用命令点名：

```
/skill:ant-output-rule
```

激活后，本次会话的每条回复都按规范写。说「停止 ant-output-rule」退出。

这个 skill 锁了自动加载。`disable-model-invocation: true` 让模型看不见它，只有你敲命令才生效。忘了激活，它完全不管事。

发汇报前跑一次检查：

```bash
python3 ~/.pi/agent/skills/ant-output-rule/scripts/check.py 草稿.md
```

退出码 0 通过，1 有硬违规，2 脚本或数据有问题。报告是候选，不是判决。

## 核心：一个骨架，三种首句

每条回复分两层。「接下来」在前，写还没发生的事。第二层在后，写已经得出的东西，层名三选一。

```markdown
**已完成：登录刷新逻辑的代码修改。iOS 端未验证。**

## 接下来

- **待确认**：重试逻辑要不要一起改。
  1. 不改（推荐）— 本次范围只含登录修复。
  2. 一起改 — 追加一项改动。
- **不做**：iOS 端真机验证 — 本机没有 iOS 构建环境。

## 已完成

**改动**

- `auth/refresh.ts`：同一时间只发一个刷新请求。

**验证**

- 未验证：iOS 端 — 本机没有 iOS 构建环境。
- 已验证：`npm test auth` — 48 项通过，0 项失败。

**原因**：两个请求一起刷新 token，后完成的那个使先拿到的失效。

**证据**：

- `auth/refresh.ts:42` — 刷新前不检查是否已有刷新在进行。
```

第一层最多四行，行首是固定的开头词：`待确认`、`下一步`、`后续`、`不做`。读者只读这四行，就知道要不要动手、还剩什么。

首句三选一。状态词开头写做过的事，「结论」或「原因」开头写答案，「待确认」开头写要读者拍板的事。

第二层的层名三选一。做过工作用「已完成」，诊断和总结用「结论」，纯回答用「答复」。

第二层写做完的事和它的依据，供核对时下翻。节名固定为 `改动`、`验证`、`现象`、`原因`、`证据`，供读者定位。节内条目按同一把尺子排：失败和阻塞在前，通过的在后。

设计依据来自 BLUF 和倒金字塔：先可行动项，后依据，读者可以随时停下。

## 文件结构

```
SKILL.md                  规范正文。R1–R37 规则、每条规则两个例子、一个输出骨架、自检清单
references/terminology.md 固定用词表。状态词、动词替换、模板节名
scripts/check.py          草稿检查脚本，纯标准库，Python 3.8+
scripts/lint_rules.py     规则例子检查脚本。核对 SKILL.md 每条规则的两个例子
scripts/harvest.py        例子采集器。按正则在仓库和会话记录里找真实句子
scripts/wordlist.jsonl    词表与句式表，81 条
tests/clean.md            合格样本，必须 0 命中
tests/bad.md              反例样本，每条带 expect 标记
examples/                 改写前后的对照示例
```

## 脚本能查什么

四类内置检查：

| 编号 | 查什么 | 规则 |
|---|---|---|
| H1 | 句子超长。中文按字数，英文按 20/25 词 | R7 |
| H2 | 分号串动作 | R31 |
| H3 | 两层顺序和节序 | R35 |
| S1 | 首句不是三种句子之一，或没按模板加粗，默认开启 | R18 |

再加词表：营销词、套话、翻译腔、造词、表演性句式。49 条硬规则，32 条软提示。

**查不了**：R30 无生命主语、R32 主谓距离、R34 定语套叠。这三条要人读。状态词用得对不对，脚本只查白名单，查不了语义。造词也查不了：词表只挡见过的词，没进表的生造词一路通过。造词靠 R29 的三问加每条规则下面的两个例子。

`scripts/lint_rules.py` 查另一件事，查的是这份 skill 自己。它读 `SKILL.md`，每条规则必须有「差」「好」两个例子，每个例子的原文必须在写的位置逐字找到，能回放的还要回放一遍。这是「每条规则两个真实例子」的执行手段。

## 改词表

每条一行 JSON，字段固定：

```json
{"id":"r29-02","level":"hard","kind":"word","value":"闭环","rule":"R29","exclude":["闭环(控制|回路|系统|调节)"]}
```

- `id` 稳定，`--disable` 用得到
- `level` 只有 `hard` 和 `soft`
- `kind` 只有 `word` 和 `pattern`
- `exclude` 可选，命中这些形式时不判

只追加，不重排。坏行会让脚本退 2 并报行号，不会静默跳过。

加测试：在 `tests/bad.md` 里写 `<!-- expect: r29-01 -->`，下一块内容应当命中这条规则。跑 `--selftest` 对账。

## 例子怎么来

每条规则下面有两行例子，形状固定：一行坏句子，一行好句子。

两行并排，读者看到的是哪里不同。好句子优先取用户原话，其次取通过检查的样本。模型自己写的句子多数不合规，从里面挑会挑错。

例子来自真实文本，写明位置，一字不改。

- 仓库内的写 `tests/bad.md:5`。
- 真实会话的写 `2026-11-06T13-12-23:196`。会话记录在本机 `~/.pi/agent/sessions/`，按时间戳找文件。
- 找例子用 `python3 scripts/harvest.py '；'`，它按正则扫仓库和本工作区的会话记录。

改完规则跑一次 `python3 scripts/lint_rules.py`。

## 依据

- ASD-STE100 的写作原则，骨架取自 [dualface/ste-zh](https://github.com/dualface/ste-zh)
- arXiv 2610.29162 的六个语言学特征，对应 R30、R32、R34 和词表
- declauding 的工程做法：确定性检查器、正反样本、改写不增事实

## 和上游的不同

本 skill 从 `ste-zh` 拷贝改写，结构上已经分叉。三处不同：

1. 多了 R26–R36，共 11 条规则，管用词、句式、首句和层内排序。
2. 所有回复改成两层结构，首句限定为三种句子。上游是一层平铺，节序是改动打头。
3. 多了检查脚本和测试样本。

术语表和示例的骨架仍与上游一致，便于对照。上游改了模板，本项目不能直接跟。

## 已知限制

- 英文只做粗略判断。混大量代码标识符的英文段落可能判错语言。
- 引号内的内容默认跳过。要查引文加 `--check-quoted`。
- 行业术语靠 `exclude` 白名单，长尾误报要靠人工判断。
- 检查器只判能机械判对错的部分。文风好坏仍需人读。

## 署名

规则骨架和术语表改自 [dualface/ste-zh](https://github.com/dualface/ste-zh)（MIT）。检查器的思路参考了 declauding 和 readable-prose 的做法，未复制它们的英文规则清单。

ADR 式的规则编号沿用上游的写法。规则正文的中文措辞为本项目改写。
